# Incident 44928272 — Signet double-paid a live redemption

**One line:** Signet paid a Coston2 redemption obligation that another party had already paid,
because `ACTIVE` on Flare does not mean unpaid on XRPL, and every guard Signet had watched the wrong
chain.

This is the most useful thing in the repository. It is a bug we found by running against the live
chain, and it is here at full strength rather than buried, because the correction is a protocol
change and the methodology that found it is the point.

---

## 1. The invariant we believed we had

> One FAssets redemption obligation produces at most one XRP payment.

Signet had three independent guards for it, and all three are real:

| guard | mechanism |
|---|---|
| registry action state | `SignetRegistry` rejects a repeated action for one `(binding, requestId, generation)` with `ActionExists` |
| coordinator database | a partial unique index permits one row in `FASSETS_COMPLETED` per obligation |
| the XRP ledger itself | a consumed account sequence is refused with `tefPAST_SEQ` |

## 2. The live setup

Coston2 redemption request **44928272**, created through the ordinary minter path: `reserveCollateral`
→ pay the agent in underlying XRP → FDC `Payment` attestation verified on chain → `executeMinting`
→ `redeem`. A genuine obligation, assigned to a real agent that was **not** Signet.

## 3. What happened

| ledger | event |
|---|---|
| 19825006 | the assigned agent paid the obligation from its own underlying address |
| — | Coston2 reported request 44928272 as `ACTIVE` |
| 19825042 | **Signet paid the same obligation again**, 36 ledgers later |

Signet's status check was correct at the moment it ran.

## 4. Why `ACTIVE` was not enough

`ACTIVE` does not mean "unpaid". It means **"not yet confirmed on Flare"**.

Confirmation is a *separate transaction* the agent submits after its underlying payment validates and
after it obtains an FDC proof. Between the payment validating on XRPL and the confirmation landing on
Flare, FAssets correctly reports the obligation as open while the payment already exists.

That window is not a bug in FAssets. It is inherent to a two-chain protocol, and any external
executor that reads only the Flare side will step into it.

## 5. Root cause

All three guards prevent **Signet** paying twice. **None of them can see a payment made by somebody
else.** They watch Flare state and Signet's own state. The obligation was discharged on XRPL, by an
address Signet does not control, and Signet never looked there.

The defect was not a missing check. It was a missing *chain*.

## 6. The correction: schema V2

Fixed at the protocol layer rather than worked around. The decision now **requires the signing
boundary's own observation of the XRP ledger**, taken across independently hosted endpoints that must
agree, and bound into the authorization commitment.

| | |
|---|---|
| ADR | [`../adr/0003-underlying-payment-precheck.md`](../adr/0003-underlying-payment-precheck.md), accepted and implemented |
| encoding | authorization preimage 431 → 468 bytes, binding the observed ledger, the source count and a root over what was found |
| obligation encoding | deliberately unchanged, so the deployed Coston2 contract still agrees |
| V1 | refused with `S001_UNKNOWN_SCHEMA`; its 62 fixtures preserved byte for byte |
| observer | `extension/internal/xrplobserve`, a second implementation of the coordinator's observer. An observation supplied by the party that wants the signature is worth nothing |

## 7. `S021_PAYMENT_ALREADY_OBSERVED`

The reason code this incident created, plus the three that cover the ways looking can fail:

| code | when |
|---|---|
| **`S021_PAYMENT_ALREADY_OBSERVED`** | a validated payment already carries this reference to this destination |
| `S022_UNDERLYING_STATE_UNAVAILABLE` | no observation, an unavailable one, or too few agreeing sources |
| `S023_UNDERLYING_STATE_DISAGREEMENT` | endpoints disagree. Deliberately not auto-retried |
| `S024_UNDERLYING_OBSERVATION_STALE` | the observation is too old to rely on |

Refusing is the default. There is no input that authorizes without an observation.

## 8. The permanent regression

[`scripts/lifecycle/incident-44928272.test.mjs`](../../scripts/lifecycle/incident-44928272.test.mjs)
replays the exact incident inputs and asserts that **no V2 input can reproduce the original
authorization**. It runs in `make verify`.

The test is named after the request id on purpose. A regression named after a live incident is harder
to delete than one named after a function.

## 9. The residual, stated rather than hidden

`S021` fires on a payment that has **validated**. Between another party submitting a payment and that
payment validating, Signet can still observe nothing and authorize.

**That window cannot be closed by observation.** Closing it needs exclusive signing authority over
the underlying account, which is exactly Signet's production architecture and is not instantiated by
this hackathon deployment.

This is a TOCTOU boundary and it is stated in the first paragraph of
[`../guarantee.md`](../guarantee.md) rather than in a footnote.

## 10. The corrected, falsifiable guarantee

> For an obligation whose only legitimate payment authority is Signet, Signet authorizes **at most
> one** payment, and refuses any payment it can observe as already made at or before the moment it
> looked.

Note what it does not say. It does not say "exactly once". It does not say anything about an
independent racer. Both were true of the claim before this incident, and neither survived it.

## 11. What this cost, honestly

No third party lost funds. **That is luck about the test setup, not a property of the system.** The
duplicate went to an address we controlled in a test where the amounts were trivial. In production it
would have been a real loss to Signet's operator.

Request 44928272 is never presented as a successful demonstration. It is the incident, and
`docs/submission-claims.md` prohibits using it as anything else.
